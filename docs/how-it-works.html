How the three-node LoRa mesh works

Three Raspberry Pi Pico 2 W boards, three SX1276 radios, one private mesh. No towers, no accounts, no cloud. Every message is encrypted on the sending board and can only be read on the receiving board. Relays in the middle move sealed envelopes they cannot open.

This guide follows a message from fingertip to air and back: hardware, radio settings, frame bytes, cryptography, pairing, storage, firmware tasks, host tools, installer, tests, and daily operation.

The idea in one page

Each operator owns one node labelled A, B, or C. Labels are convenience names for humans; the air never trusts them. When A sends to B, A's firmware seals the text with a key only A and B share, addresses the frame to B's current hourly alias, and transmits at the lowest power the radio supports (+2 dBm). B answers with an encrypted acknowledgement. If B is out of range, C can forward the sealed frame once, without reading it.

Trust boundaries

ZoneSees plaintextSees sealed bytes
Sending and receiving firmwareYes, its own endsYes
Relaying firmwareNoYes, header plus opaque body
Host computer (Python tools)Typed text and received textOpaque pairing records only
Passive radio listenerNoYes, but authentication fails without keys

Cryptography lives in Rust on the board. Python never agrees keys and never encrypts. That single-implementation rule is what keeps every node byte-identical.

Hardware and wiring

Three identical nodes. Each node is a Raspberry Pi Pico 2 W (RP2350) wired over SPI to an Adafruit RFM95W breakout (Semtech SX1276), with a 915 MHz antenna on the breakout's antenna pad. There are no wires between nodes. Power is USB only.

Only DIO0 is wired. DIO1 is not needed for this protocol. Leave the breakout's EN pin unconnected (it pulls high internally). SPI runs at 1 MHz during bring-up. Use GPIO numbers from the silkscreen, never physical pin counts, and verify with the official Pico 2 W pinout before powering.

Antenna rule. Fit an antenna on every radio before any transmission. Transmitting with no antenna can destroy the power amplifier. Check continuity end to end with power off, and confirm there is no short between 3V3 and ground.

Short airtime is a privacy feature here: fewer milliseconds on air means a smaller window for direction finding and collisions.

Frame bytes

Everything on air fits in 255 bytes. A 28-byte header names the envelope, a variable body carries the payload, and a 2-byte CRC guards the trip. The body-length byte sits at offset 27 and counts the 16-byte authentication tag in secure mode.

Decoding is strict: unknown versions, stray flag bits, hops above 1, length mismatches, bad CRC, malformed lab bodies, and wrong acknowledgement shapes are rejected. Secure bodies stay opaque until the receiving endpoint authenticates them, then the decrypted bytes are validated the same strict way.

Encryption and keys

Each pair of contacts shares one 32-byte root secret established at pairing. Everything else is derived from it with HKDF-SHA256 under distinct labels, so traffic keys, address keys, and confirmation keys never overlap.

Hourly traffic keys

For each hour, each direction gets a fresh key: HKDF(root, "LMESH-hour-v1" || hour). Messages are sealed with ChaCha20-Poly1305. The nonce is the hour plus the sequence number, so it never repeats within a key's lifetime. The authentication covers the immutable header plus the body, which is why a relay cannot alter addresses or replay bytes without the receiving endpoint rejecting them.

Hourly addresses

Aliases rotate every hour: first_4(HMAC(secret, "LMESH-addr-v1" || identity || hour)). A relay sees aliases change but cannot link them without the secret. Four bytes can theoretically collide; the cryptography decides identity on decryption, never the alias match alone.

Replay defense

Each contact keeps sliding windows of recently seen sequence numbers for messages and acknowledgements, plus an anchor hour that only moves forward with trusted local time. A duplicate, a late retry outside the window, or a frame from a distant hour is dropped. Sequence numbers are reserved in durable blocks of 32 before use, and the whole last block is skipped after a reboot, so a power cut can never reuse a nonce.

ChaCha20-Poly1305 was chosen because the RP2350 has no AES accelerator; software AES there is slower and harder to keep constant-time.

Pairing new contacts

Pairing happens in person with radios off. The boards exchange three records through QR codes and files carried by the host computer. The host only transports opaque text; it never sees keys.

StepRecordWhat it carries
Offer98 bytesVersion, long-term signing key, fresh ephemeral key, fresh challenge
Proof122 bytesTranscript hash, role byte, sealed identity, signature
Confirmation66 bytesTranscript hash, role byte, confirmation code

Each record travels as LMESH1: followed by unpadded base64url, shown as a QR PNG. Both operators compare the 16-character transcript fingerprint on their screens before confirming; on any mismatch the pairing is abandoned, never auto-accepted. One attempt is pending per board at a time, expiring after 10 minutes. Restarts discard temporary secrets, so resuming needs fresh offers.

Radio-off precondition. Pairing commands refuse to run while the radio is enabled, and report RADIO_MUST_BE_OFF. Keys are never exchanged over the air.

Node engine

crates/mesh-node/src/engine.rs is the transport-independent brain shared by firmware and host tests. It owns the pairing ceremony state, encrypted send and receive, relay decisions, blocking, and the durability contract. It is no_std, uses fixed buffers, and wipes secrets when done.

Durability contract

Every mutation with a visible effect is staged into a snapshot first. The caller writes the snapshot to flash, then calls commit_ok. Only then does the engine emit the frame or delivery event. An interrupted write can therefore never reuse a nonce, clear a replay window, or resurrect a retired hour.

Send path

Begin reserves a sequence number and stages the snapshot. The firmware commits it, transmits with channel detection, and waits up to 12 seconds for the acknowledgement, retrying at most 3 times. Completion, failure, channel-busy, and cancellation each produce an honest report; nothing claims success without an acknowledgement.

Receive path

Frames authenticate against each contact's directional keys across the current and adjacent hours. On success the endpoint validates the decrypted body, advances replay state, queues its own acknowledgement as a fresh envelope with an independent packet ID, and either delivers the text or schedules one relay forward. Relays without keys run structural checks only and forward opaque bytes.

Blocking

Blocking is local to the board: a blocked contact cannot send or complete, and the policy gate invalidates its transmit tokens immediately. There is no network-wide ban and no automatic beaconing, both deliberately rejected as incompatible with the privacy goals.

What survives reboot

The top 64 KiB of the 4 MiB flash holds a sequential-storage map with three independent keys. Firmware code is capped below it at link time, so code can never overlap storage.

KeyRecordContents
0x01 nodeLMSH v3, about 3.5 KiBProvisioning, label, identity keys, clock floor, 16 contact slots with roots, sequence reservations, replay windows
0x02 settingsLSET, 13 bytesTunable transmit and relay parameters with clamped ranges
0x03 wifiWSET, 102 bytesSSID and passphrase in plaintext flash (readable with physical access; never logged or printed)

Old two-slot records migrate by zero-filling the new slots and re-encoding canonically. Unknown magic or versions fail closed to a fault state that disables secure operations rather than regenerating keys quietly. The clock itself is RAM-only: every boot starts unset until the USB computer sets trusted UTC, and time can never move backwards past the highest transmitted hour.

Boot order

Load persisted state, then settings, then the WiFi credential. Initialize the hardware random generator, detect the radio over SPI, start the WiFi task, the radio task, and the runtime task, then serve USB. Replies terminate every line with a newline byte; a missing terminator once stalled every radio-image reply and is now covered by an explicit write after the chunk loop.

Operator commands on USB status, contacts, provision, time set, time status, radio on, radio off, radio arm-next-boot, ping, send, block, unblock, contact delete, pair offer, pair proof, pair confirm, pair import, settings get, settings set, wifi status, wifi set, wifi forget.

USB and TCP wire

Host and board speak newline-delimited JSON. Each request carries an integer id and a string op; replies echo the id with ok plus a result or an error string. Asynchronous receive events carry event instead. Request lines are capped at 1024 bytes; replies at 4096.

{"id": 1, "op": "status"}
{"id": 1, "ok": true, "result": {"label": "C", "image": "radio-secure", ...}}

One process owns a port at a time through a lock file; a second opener gets PORT_BUSY. Deadlines are bounded (5 seconds default, up to 120 for long sends) so a silent peer cannot hang the operator. The WiFi TCP server on port 7777 carries the identical wire for untethered use. Error strings are frozen contract: BAD_REQUEST, CONTACT_BLOCKED, RADIO_UNAVAILABLE, RADIO_MUST_BE_OFF, STORAGE_FAULT, UNKNOWN_OP, PORT_BUSY, LINE_TOO_LONG.

Host tools

meshctl is the Python terminal interface. It holds no keys: it frames bytes, moves opaque pairing records between firmware and QR PNG files, and reads or types plaintext.

Boards are identified by matched status labels, never by USB device numbers, which shift across reboots. Pairing images, diagnostic captures, and plaintext history live under .mesh-local/ and stay out of version control.

Web installer

web-installer/ is a static page with no build step. It lists releases from releases.json, each with a file URL and SHA-256 hash so the download is verified before copying. Flashing is a file copy onto the BOOTSEL mass-storage volume; the board reboots itself when the copy finishes. Serve the directory over plain HTTP on localhost. The page states plainly that the private mesh is the default and that any compatibility mode would be labelled insecure and is never enabled here.

Test scripts

Run regression first, then the focused scripts for diagnosis. The mesh scripts take no port arguments: boards are discovered by USB identifiers and matched by live status labels.

ScriptProves
mesh_regression.pyThree boards present and provisioned, all six directed legs acknowledge exactly once, bad slots fail without airtime, quiet radios stay quiet
mesh_allways.pyExplicit per-edge send matrix, overridable per direction with slot numbers
mesh_adversarial.py1-byte and 160-byte boundaries, oversize and empty rejection, hostile bytes, blocking, five-message burst with exact-once delivery
radio_smoke.py, radio_link.py, radio_silence.pySingle-purpose bring-up, link, and silence checks for one board or one pair

Retry posture is 3 attempts with 12-second acknowledgement waits. Radios are left off after regression; re-enable per board before manual operation. Native Rust tests cover framing, cryptography, pairing codecs, replay windows, relay cache, and clock rules without hardware.

Meshtastic note

Compatibility with the public Meshtastic protocol is proposal only. The physics verdict stands: same-radio interoperation is impossible, because frequency, spreading factor, bandwidth, preamble, and sync word all differ (915.0 vs 906.875 MHz, SF7 vs SF11, BW500 vs BW250, 8 vs 16 preamble symbols, private 0x12 vs public sync). One radio hears the other mesh as noise. A bridge would need a second dedicated radio, host-side display policy, and explicit insecure labelling, and transmit from our side is not proposed.

What exists is a decode-only helper (crates/mesh-core/src/compat.rs, behind a non-default feature) plus a host receive-only parser. Compat bytes travel inside an authenticated private message and are decoded only after endpoint decryption. It adds no transmit path, no shared-key handling, and no bridging.

Limits and non-goals

No store-and-forward: an unreachable recipient fails after retries rather than queueing. No beacons, no network-wide bans, no GPS or ranging in this build. Clocks need the USB computer after every long power-off. WiFi credentials sit in plaintext flash, so physical access means credential access; the design documents that rather than hiding it. Home routers with device approval lists may refuse the boards entirely; USB remains the primary path and loses nothing. US operation is unlicensed under FCC Part 15 at this power and duty cycle, but configured bandwidth and power settings are not a substitute for calibrated measurement or certification.
